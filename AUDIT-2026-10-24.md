# Audit complet — MCP Command Center

**Date** : 2026-10-24 · **Version** : 0.7.0 · **Branche** : `main` (beaucoup de travail non commité, cf. §7)
**Périmètre** : audit statique de tout le code Rust (`src/` 8 803 lignes, `desktop/`), UI embarquée, boutiques, config/cache locaux, CI, hygiène du dépôt. Suite de l'audit du 2026-10-19 (v0.6.3).

---

## 1. Verdict global

Le projet a **énormément progressé depuis l'audit v0.6.3** : les P0/P1 sécurité de l'époque sont traités (auth API, kill_port exact, caps HTTP, anti double-spawn, seeds en échec bornés, https refusé, dossier Filesystem explicite), la baseline est verte (**61/61 tests, 6,4 s**) et les nouvelles briques (boutique 4 catalogues, pairs LAN, découverte SSH, autostart, cache de démarrage) sont testées et proprement écrites — le sanitize SSH (`ssh_safe` + `mcp_path_safe`, testés contre l'injection) est un vrai bon travail.

**Mais le mécanisme d'authentification v0.6.6 a un trou qui le vide de sa substance** : la page `/` est servie **sans authentification** et embarque le code d'accès API en clair. En bind `0.0.0.0` (la config actuelle de cette machine), **n'importe quel hôte du LAN fait `GET /` et lit le code**, puis appelle `/api/*` normalement — y compris `add` stdio + `start` = exécution de commande arbitraire. C'est le P0 de cet audit. Deuxième trou du même secret : la découverte de pairs **diffuse le code à ~254 hôtes du LAN** au boot. Enfin, le secret traite en clair dans des fichiers non gitignorés (`ui-e2e-*`) à un `git add -A` d'être publié.

En l'état, le garde « code d'accès » protège contre un balayeur de ports paresseux, pas contre un attaquant LAN déterminé.

## 4. Sécurité — nouveaux constats

### S-A — P0 : le code d'accès API est servi publiquement par `GET /`
`src/lib.rs:501-510` : la route `/` remplace `__MCC_ACCESS__` par `settings.api_access` **sans aucun contrôle d'accès** (le garde de `check_access` ne couvre que `/api*`, `lib.rs:141`). La page HTML contient donc `const MCC_ACCESS = '0ea5…'` pour quiconque peut joindre le port — c'est exactement ainsi que les fichiers `ui-e2e-script.js:4` et `ui-e2e-config.json:161` ont capturé le code.

Scénario : `ui_bind: "0.0.0.0"` (config actuelle, requis pour les pairs) → n'importe quel hôte du LAN : `GET http://<ip>:5090/` → extraction du code → `POST /api/action {"action":"add","transport":"stdio","program":"…","args":[…]}` → spawn immédiat (`poll_one` → `probe_stdio`) → **exécution de commande arbitraire**. La chaîne Host/Origin/Content-Type est inutile contre un client non navigateur qui a le code.

Fix recommandé : ne plus servir le code dans la page. Au choix : (a) `/` renvoie une mini-page de login qui stocke le code dans `localStorage` (le monkey-patch `fetch` de `ui.rs:388` l'embarque déjà partout) ; (b) `/` exige `?access=` et la UI le mémorise ; (c) session cookie émise après un POST de vérification. Option (a), 20 lignes, garde l'UX actuelle après la première saisie.

### S-B — P1 : `discover_peers` diffuse le code d'accès à tout le LAN
`manage.rs:2298-2310` + `probe.rs:1486-1490` : la sonde de pairs envoie **notre** code en clair (`X-MCC-Access`) à chaque IP ARP sur les ports 5090-5091, au boot (`network_enabled: true` par défaut, `lib.rs:328-343`). Un hôte malveillant qui écoute sur 5091 **reçoit le secret sans le demander** — c'est l'inverse d'un protocole de preuve. Combiné à S-A c'est redondant, mais il resterait actif même si S-A était corrigé.

Fix : handshake à preuve — le sondeur envoie un nonce, le pair répond `HMAC(nonce, code)` ; ou plus simple : liste `peers_autorises` explicite dans la config, aucune diffusion aveugle. À défaut, ne sonder que les hôtes enregistrés (`ssh_hosts`/pairs connus).

### S-C — P1 : le secret traite en clair dans des fichiers non gitignorés
- `ui-e2e-config.json:161` et `ui-e2e-script.js:4` contenaient le code d'accès en clair (rédigé ici ; fichiers supprimés, code tourné) — non ignorés par git (vérifié `git check-ignore`, exit 1).
- `config.json:354` : le code en clair (gitignoré, correct) ; `config.json:404` : `ui_bind: "0.0.0.0"` → exposition LAN réelle sur cette machine.
- `state-cache.json` (98 Ko, non ignoré) : pas de secret, mais **cartographie d'infra** : 32 serveurs, 12 endpoints LAN internes (`192.168.40.x`), chemins locaux, historique d'erreurs.

Un `git add -A` publie tout ça. **Rotation du code recommandée après le nettoyage** (il a de plus été broadcasté sur le LAN, cf. S-B). `.gitignore` : ajouter `state-cache.json`, `ui-e2e-*`, `pauvre-router-audit/`, `nul`, `patch_*.py`, `store_patch.py`, `.zwork/`.

### S-D — P2 : desktop Tauri — CSP `null` + `withGlobalTauri: true`
`desktop/tauri.conf.json:10,12` : l'UI distante (chargée en HTTP depuis le core) a `window.__TAURI__` injecté et **aucune CSP**. L'échappement XSS de l'UI est actuellement irréprochable (vérifié : `esc()` systématique, `js()` double-échappe dans les attributs, aucune interpolation non échappée trouvée), mais un seul oubli futur = accès complet aux API Tauri depuis une page réseau. Défense en profondeur : poser une CSP minimale (`default-src 'self' http://127.0.0.1:* http://localhost:*; connect-src 'self' …; script-src 'self' 'unsafe-inline'`) — l'UI est mono-page inline, ça se calibre en une heure.

### S-E — P2 : capability desktop non commitée + wildcard de ports
`desktop/capabilities/main-remote-ui.json` et `desktop/icons/icon.icns` sont **untracked** : un clone frais (ou la CI) construit un desktop sans capability → drag/close de la fenêtre sans décorations cassés ailleurs. Et `"urls": ["http://127.0.0.1:*", "http://localhost:*"]` autorise tout port local au lieu des 5090-5099 documentés. À committer (les `src/store_*.rs`, `src/logos.rs`, `assets/*.png` aussi) et resserrer les ports.

### S-F — P3 : durcissements divers (non urgents, LAN de confiance)
- `check_update` (`manage.rs:1431-1444`) : passe par **PowerShell** → silencieusement inopérant sur Linux/macOS (et un spawn PowerShell/heure côté Windows). Portage `curl` si présent, ou rustls à terme.
- `http_post_host`/`sse_get_host`/`health_ok_host` : **lectures non plafonnées** (le parseur d'entrée HTTP est capé, pas le client) — un serveur LAN rapide peut gonfler la RAM pendant la fenêtre de timeout. Cap ~2 Mo comme côté serveur.
- `ssh_safe` autorise un `-` initial (option-injection ssh théorique : `user="-o…"` reste bloqué par l'absence de `=`/espace, mais rejeter un `-` initial est gratuit).
- Injection d'en-têtes possible dans la requête de sonde via un `path` contenant `\r\n` (config only, impact = cible déjà choisie par l'opérateur) — sanitiser le path côté client comme `mcp_path_safe` le fait côté SSH.
- Slowloris : 64 connexions × 30 s de timeout de lecture (rien de nouveau, LAN).
- Comparaison du code d'accès non constant-time, `generate_access()` sur `RandomState` (documenté, entropy OS correcte en pratique), collision d'id possible sur `now_compact()` (ms).
- `state_json` expose `ssh_hosts` (ip+user) à tout client loopback sans auth — info-disclosure locale mineure.

## 5. Robustesse / bugs fonctionnels

### F-A — P1 : panic index out-of-bounds dans `import_mcp_text`
`manage.rs:1071-1075` : `if toks.len() >= 3 && toks[0]=="claude" && …` puis **`toks[3]` et `toks[4]`** — un `POST /api/action {"action":"import_mcp","text":"claude mcp add"}` (3 tokens) ou `…add nom` (4 tokens) fait **paniquer le thread HTTP** : pas de réponse, connexion coupée, reproductible à volonté. Fix : exiger `toks.len() >= 5` + test.

### F-B — P2 : `kill_port` reste un no-op hors Windows
`probe.rs:168-169` (transporté de l'audit v0.6.3, item F2). Le desktop est distribué pour 4 cibles ; sur Linux/macOS, « Stop » sur un serveur HTTP laisse le process détaché en vie (la boucle de vérification finit en timeout 10 s). Fix : `ss -tlnp`/`lsof -ti :PORT` → kill, ou spawn non détaché sur unix.

### F-C — P2 : `check_update` Windows-only
Voir S-F : l'UI affiche jamais de mise à jour dispo sur Linux/macOS. Bascule vers `curl` (présent partout) avec fallback PowerShell.

### F-D — P2 : `scan_network_range` = 1 thread par hôte (254+)
Borje acceptable en LAN, mais sur une machine multi-interfaces VPN, chaque préfixe /24 spawn 254 threads de plus. Un pool borné (ex. 64 workers) suffirait. P3 si le LAN est petit — P2 si l'usage VPN est courant.

### F-E — P3 : warning clippy `--all-targets`
`manage.rs:1276-1281` : le `return` sous `#[cfg(test)]` de `apply_autostart` rend `let args` inatteignable en build test. La CI ne le voit pas (clippy sans `--all-targets`), mais c'est un futur échec si on resserre la CI. Fix : `#[cfg(test)] let args = args;` non — simplement conditionner le corps, pas de return anticipé.

### F-F — P3 : divers
- `test_state_helper()` vide (`manage.rs:4099-4100`) — mort.
- Scripts one-shot `patch_066.py`, `store_patch.py`, `scripts/patch_appstate_tests.py` : appliqués et obsolètes, à supprimer ; `nul` (parasite Windows) à supprimer via `del "\\.\C:\...\nul"` ; `pauvre-router-audit/` est **un dépôt git complet niché** dans le repo — à déménager hors du projet.
- `start-command-center.bat:8` : `start` sans vérifier que le build a réussi.
- `examples/test-http-server.js:26` : `.listen(port, '::')` écoute sur toutes les interfaces (commentaire annonce `[::1]`) — la fixture de test expose un faux MCP au LAN pendant les tests.
- Logs : `println!` seulement — rien sur disque en mode desktop fenêtré (déjà noté en v0.6.3, toujours vrai).
- CI : actions épinglées par tag flottant, pas par SHA (`checkout@v4`, `dtolnay/rust-toolchain@stable`…) ; `permissions: contents: write` au niveau workflow au lieu du job release ; aucune CI sur push/PR (les tests ne tournent qu'au tag).

## 6. Points forts (à préserver)

- **Sanitize SSH exemplaire** : `ssh_safe` (rejet injection, testé), `mcp_path_safe`, payload sans quote, session id `tr -cd 'A-Za-z0-9-_'`, BatchMode+accept-new, timeout clampé. La feature la plus risquée du projet est aussi la mieux défendue.
- **XSS maîtrisé** sur des données non fiables (noms/versions/tools de serveurs MCP distants inconnus) : `esc()` appliqué partout y compris journal et erreurs, `js()` pour les attributs onclick, `langChip`/badges sur clés fermées. Audit ligne par ligne : aucune interpolation non échappée trouvée.
- 61 tests qui testent le **protocole** (fake serveurs HTTP/SSE/stdio, contrat pairs, fingerprint litemcp à deux signaux, netstat par colonne, roundtrip config) ; les régressions des audits précédents ont chacune leur test.
- Anti-DoS d'entrée (2 Mo / 64 conns / headers capés), écriture config atomique, garde anti double-spawn, désactivation auto-restart après 3 échecs, ordre de verrouillage cohérent (servers→children) — aucun deadlock identifié.
- Zéro dépendance réseau (std + serde_json), surface supply-chain minimale, Cargo.lock commité, versions cohérentes 0.7.0 partout.
- UI : drag & drop réordonnable, replis à état persisté, conf-agent copiable, boutique à logos — le tout dans un seul fichier sans framework, lisible.

## 9. Conclusion

L'exécution du plan d'action v0.6.3 a été sérieuse : 12/13 items corrigés avec tests de régression, et les nouvelles features arrivent avec leur sanitize et leurs tests — c'est rare et mérite d'être dit. Le point noir est que la **protection phare v0.6.6 (code d'accès) repose sur un secret distribué publiquement par la même app** : tant que `/` sert le code et que `discover_peers` le broadcast, l'auth API est cosmétique. Les items 1-2 ci-dessus sont une demi-journée de travail et transforment réellement le modèle de menace ; le projet redevient alors ce qu'il prétend être — un centre de contrôle LAN convenablement fermé.
