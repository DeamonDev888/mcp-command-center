# Audit complet — MCP Command Center

**Date** : 2026-10-19 · **Version** : 0.6.3 · **Commit** : `7c38c15` (+ 2 fichiers modifiés non commités, voir §8)
**Périmètre** : audit statique de tout le code Rust (`src/` 5 534 lignes, `desktop/`), UI embarquée, config, CI/release, baseline d'exécution.

---

## 1. Verdict global

Projet **sain et bien conçu** pour son usage réel (pilotage local des serveurs MCP de la machine) : zéro dépendance réseau (std + serde_json), parseur HTTP/JSON-RPC maison propre, UI sans XSS détecté, tests qui testent le vrai protocole, CI stricte. Baseline exécutée : **34/34 tests OK, `cargo fmt --check` OK, `cargo clippy` 0 warning**.

Le talon d'Achille est **réseau** : l'API n'a aucune authentification (connu, documenté P0 dans le README, toujours non traité en 0.6.3) et l'audit y ajoute **deux aggravations non documentées** — le CSRF cross-origine possible depuis un navigateur, et l'exécution de commande arbitraire offerte par l'action `add`. En l'état (`ui_bind: 0.0.0.0` par défaut, cf. `types.rs:134`), **n'importe qui sur le LAN peut démarrer/arrêter/ajouter des serveurs, tuer des process et exécuter une commande arbitraire sur la machine**.

## 3. Constats sécurité

### S1 — CRITIQUE : API sans auth + RCE via `add`, atteignable depuis le LAN **et** depuis le navigateur
- `route()` (`src/lib.rs`) ne vérifie **aucun token/Origin/Host** sur `/api/*`. Bind par défaut `0.0.0.0` (`types.rs:134`), requis pour la détection de pairs.
- **RCE directe** : `POST /api/action {"action":"add","transport":"stdio","program":"<n'importe quoi>","args":[...]}` → spawn immédiat (`poll_one` → `probe_stdio`) d'un programme arbitraire avec arguments et workdir arbitraires. `install_store` enchaîne en plus `npx -y` / `uvx` **sans sandbox** (14 items du catalogue).
- **Aggravation non documentée (CSRF)** : toutes les réponses portent `Access-Control-Allow-Origin: *` (`lib.rs:200`) et le body de `/api/action` est parsé comme JSON **quel que soit le Content-Type**. Un site web visité par l'opérateur peut donc poster le body en `text/plain` (requête « simple », sans préflight) → l'action s'exécute, et la réponse est même lisible grâce à l'ACAO `*`. Chrome atténue via Private Network Access (préflight PNA que ce serveur ne répond pas — pas de handler OPTIONS), mais pas Firefox/Safari, et le **DNS rebinding** (aucune validation du header `Host`) contourne tout. `GET /api/state` est lisible cross-origin : fuite de la topologie MCP interne.
- Impact combiné : depuis le LAN → contrôle total (RCE, kill de process, scan réseau) ; depuis un navigateur piégé → idem selon navigateur.
- **Fix recommandé (P0, aligné roadmap #1)** : token obligatoire dès que bind ≠ 127.0.0.1 (header `X-MCC-Token`, généré au premier boot, affiché dans l'UI/desktop), refus de tout `Origin`/`Host` non attendu, handler `OPTIONS` qui répond 403, et refuser les POST dont le Content-Type n'est pas `application/json`. Alternative pragmatique si les pairs restent voulus : auth par token partagé pair-à-pair.

### S2 — ÉLEVÉ : `kill_port()` tue le mauvais process (match par sous-chaîne)
`probe.rs:92-94` : `needle = ":3141"` matche aussi `:31410`…`:31419` dans `netstat -ano` (et toute ligne LISTENING contenant la sous-chaîne). `taskkill /F /PID` est appliqué à **tous les** PIDs des lignes matchées. Combiné à l'API sans auth (ajouter un serveur sur n'importe quel port puis `kill`), un attaquant peut arrêter un service arbitraire de la machine. Fix : parser la colonne d'adresse et comparer le port **exact** (comme le fait déjà `build_port_owner_map` avec `rsplit(':')` + `parse::<u16>()`), restreindre à `127.0.0.1`/`[::1]`.

### S2 — ÉLEVÉ : corps de requête HTTP illimité + thread par connexion
`lib.rs:176-188` : les en-têtes sont plafonnés à 1 MiB, mais la boucle `while body.len() < content_length` (`lib.rs:182`) suit un `Content-Length` choisi par le client **sans plafond** — un émetteur qui poste en continu gonfle la RAM jusqu'à couper. Chaque connexion spawn un thread sans limite (read timeout 30 s) → épuisement trivial depuis le LAN. Fix : cap dur (ex. 2 MiB) sur le body + semaphore/limite de connexions concurrentes.

### S3 — MOYEN : `Host: localhost` envoyé aux hôtes distants
`http_post_host` (`probe.rs`) construit `Host: localhost` en dur. Sur un MCP distant derrière un vhost/reverse-proxy, la requête est mal routée ou rejetée. Fix : `Host: <host>:<port>` quand `host` est explicite.

### S3 — MOYEN : `https://` accepté mais TLS inexistant → badge « HTTPS » trompeur
`parse_url_parts` accepte `https://` (port 443), mais le client n'a pas de TLS : toute URL https sonde en clair et finit DOWN avec une erreur cryptique. Le badge UI « HTTPS » (`ui.rs`, v0.6.1) est en réalité « port 443 », pas du TLS. Fix court : refuser `https://` à l'import avec un message clair ; moyen terme : rustls (roadmap README).

### S3 — MOYEN : `install_store` Filesystem expose tout le profil utilisateur
`manage.rs:456-462` : l'item « Filesystem » embarque `C:/Users/Deamon` en dur (chemin perso **et** périmètre maximal : lecture/écriture du profil entier offert au serveur MCP installé). Fix : demande du dossier à l'install (champ vide = refus) et ne jamais embarquer de chemin utilisateur dans le catalogue distribué.

## 4. Constats fonctionnels / robustesse

### F1 — Élevé : seeds avec chemins perso → boucle de respawn infinie sur machine cliente
`default_servers()` (`manage.rs:29`) embarque `C:/Users/Deamon/Desktop/Backup/Serveur MCP/...` et `C:/SierraChart/...` dans le binaire distribué. Sur toute autre machine (ou si le dossier disparaît), les 4 seeds activés ont `start_cmd` + `auto_restart=true` → **à chaque cycle de poll (15 s), `spawn` échoue, log warn, et on réessaie indéfiniment** — pas de backoff, pas de désactivation après N échecs, log saturé. Fix : après N échecs de spawn consécutifs, repasser `auto_restart=false` + état dédié (« START-FAILED »), et faire des seeds opt-in quand le chemin n'existe pas au boot.

### F2 — Moyen : Stop HTTP cassé hors Windows alors que la 0.6.3 distribue desktop Linux/macOS
`kill_port` est un no-op `#[cfg(not(windows))]` (`probe.rs:110`). Or `child.kill()` ne tue que le launcher `launch.cjs`, pas le serveur détaché (commentaire du code). Sur Linux/macOS, « Stop » laisse le serveur UP (la boucle de vérification finit en timeout 10 s sans succès). La CI publie pourtant 4 desktops multi-OS depuis la 0.6.3. Fix : portage `kill_port` (parse `ss -tlnp`/`lsof -ti :PORT` → kill) ou spawn **sans** détachement sur unix pour garder le handle du vrai process.

### F3 — Moyen : `local_ips()` ne parse pas `hostname -I`
`manage.rs:1301-1330` filtre les lignes contenant « ipv4 », mais `hostname -I` (source déclarée pour unix) ne sort que des IP sans marqueur → sur Linux/macOS, `local_ips()` ne retourne que le fallback UDP (IP de la route par défaut). Les sous-réseaux des interfaces secondaires sont manqués pour le scan réseau et la détection de pairs. Fix : sur unix, parser directement les tokens IP de `hostname -I`.

### F4 — Moyen : course double-spawn entre poller et actions API
`poll_one` (auto-start HTTP et restart stdio) teste `child_alive` puis spawn **hors** du verrou. Le thread poller et un `POST /api/action refresh|toggle|start` simultané peuvent passer le gate tous les deux → deux spawns. Fenêtre étroite mais réelle. Fix : verrou par-id (ou verrou global court) autour de check+spawn.

### F5 — Faible : erreurs d'écriture de config avalées
`save_config` termine par `std::fs::write(...).ok(); std::fs::rename(...).ok();` → un disque plein/ACL refusée perd l'ajout **silencieusement** (l'UI montre le serveur jusqu'au reboot). Le tmp+rename est par contre un bon choix atomique. Fix : logger en `error` sur échec (et remonter `ok:false` quand pertinent).

### F6 — Faible : suppression d'un seed non persistable
`remove` sur un seed fonctionne en mémoire, mais `load_config` réinjecte toujours les 7 seeds → au reboot, le seed revient. L'interrupteur `toggle` (persisté) est le bon outil ; soit l'assumer (masquer « Retirer » pour les seeds), soit persister une liste d'exclusion.

### F7 — Faible : divers
- `config.json` local (non commité) active `debats`/`NEWS_BTC`/`NEWS` et contient 2 entrées démo orphelines (`sse-demo` 3170, `py-header` 3171 sans programme) sondées en boucle → bruit PORT-ONLY/DOWN. Nettoyage ponctuel.
- `ui-dist/index.html` hardcode la redirection vers le port 5090 (fallback mort si le port a sauté) — inoffensif aujourd'hui (le desktop navigue vers l'URL réelle), à supprimer ou générer.
- Logs : `println!` uniquement ; en mode desktop Windows (`windows_subsystem = "windows"`) tout part dans le vide — aucun trace disque. Un fichier de log rotatif aiderait le support.
- `refreshAll()` UI : rafraîchit les serveurs séquentiellement (N × timeout possible) — paralléliser ou appeler un futur `refresh_all`.
- README : la section « État actuel sur cette machine » dit debats/NEWS désactivés, la config locale les a activés depuis — drift de doc mineur.

## 5. Points forts (à préserver)

- **Surface de dépendances minimale** (serde_json seul côté core ; tauri côté desktop) — supply-chain très réduite, `Cargo.lock` commité.
- **UI sans XSS détecté** : `esc()` appliqué systématiquement (labels, tools, journal — y compris les données venues de serveurs MCP distants non fiables), attributs `onclick` protégés via `js()` qui double-échappe. Bon travail sur un point rarement maîtrisé.
- **Modèle d'états UP / PORT-ONLY / DOWN / DISABLED** bien pensé et bien testé (le piège classique du moniteur binaire est traité).
- Client HTTP maison correct pour son périmètre : chunked + SSE + Content-Length, deadlines propres, statut 2xx exigé, détection de zombies.
- `config.json` écrit en atomique (tmp + rename), `refresh_secs` clampé 5..3600, verrous cohérents (ordre servers→children respecté partout, `lockv` récupère les mutex empoisonnés — pas de deadlock identifié).
- Tests qui valident le **protocole** (fake servers HTTP/SSE/stdio, contrat `/api/state` des pairs, rejet du non-MCP) et pas seulement des fonctions pures ; le bug fondateur v0.1 (stdio sans start_cmd jamais redémarré) a son test de non-régression.
- CI stricte (fmt implicite au rituel, clippy `-D warnings`, tests avant build) et release reproductible par tags.

## 10. Conclusion

Le cœur technique est de bonne facture et les fondamentaux (tests, fmt, clippy, atomicité de config, hygiène XSS) sont solides. Le projet est **aujourd'hui une console d'administration sans porte de sortie sécurisée** : tant que les items 1-2 ne sont pas traités, il doit rester considéré comme un outil mono-utilisateur de confiance sur un LAN de confiance, et ne jamais être exposé (port forward, Wi-Fi partagé, machine multi-usage). La bonne nouvelle : le P0 est exactement celui que le README s'était déjà prescrit — il ne manque que l'exécution, et l'audit précise le détail des mécanismes (CSRF sans préflight, kill par sous-chaîne) à couvrir en même temps.
