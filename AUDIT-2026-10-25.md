# Audit complet — MCP Command Center

**Date** : 2026-10-25 · **Version auditée** : 0.7.7 (HEAD `9b71819`, `main` ahead 10 sur origin/main)
**Périmètre** : code Rust complet (`src/` 10 273 lignes, `desktop/`), UI embarquée, boutiques, config/cache locaux, CI GitHub Actions, hygiène git, packaging Tauri.
**Méthode** : lecture intégrale + audits parallélisés (4 agents) + **vérification dynamique contre l'instance live** (release installée, bind `0.0.0.0:5091`) + fuzz du parseur HTTP + comparaison binaire pré/post correctif.

---

## 1. Verdict global

Le projet est **nettement plus mûr qu'au rapport précédent**. Les 13 constats de l'audit du 2026-10-24 sont **tous corrigés**, chacun vérifié dynamiquement et non pas seulement lu dans le code :

- le code d'accès API n'est **plus** servi dans la page (`GET /` ne contient pas le secret — testé),
- la découverte de pairs ne diffuse **plus** le secret (preuve HMAC-SHA256 à usage unique — testé, y compris le rejeu),
- `import_mcp_text` ne panic plus, `kill_port` fonctionne sur Unix, la CSP est posée, la CI tourne sur push/PR avec actions épinglées par SHA.

**Quatre vrais défauts subsistent**, tous deux trouvés et reproduits par moi pendant cet audit, tous **corrigés et testés** :

| # | Défaut | Sévérité | Statut |
|---|---|---|---|
| **A.1** | **Panic du parseur HTTP** (réponse < 4 octets) → le thread du *poller* meurt en silence : la supervision s'arrête **définitivement** | **P1** | ✅ **corrigé + testé** |
| **A.2/A.3** | **2 panics de `dechunk()`** (chunk tronqué → slice hors bornes ; taille hexa absurde → overflow usize) → même effet | **P1** | ✅ **corrigé + testé** |
| **B** | **XSS stockée** : les statistiques d'un pair distant sont interpolées sans échappement → exécution de JS dans l'UI | **P0** | ✅ **corrigé + testé** |
| **C** | La lecture stdio (`BufRead::lines`) **n'a aucun plafond** de taille de ligne (300 Mo alloués d'un bloc) | **P2** | ✅ **corrigé + testé** |

La **cause racine commune** des trois panics : le code est correct mais son *failure mode* est fatal et **totalement silencieux** (aucun `catch_unwind` dans le projet, et en mode desktop `windows_subsystem = "windows"` → aucune console). Un `panic::set_hook` qui journalise sur disque reste recommandé (item 5 du plan d'action).

Aucun P0 théorique ne s'est avéré exploitable : le modèle de menace tient. Testé en direct — une action `add stdio calc.exe` (RCE) depuis le LAN **sans** le code d'accès est bien rejetée en **401**.

## 4. Défaut A — P1 : trois panics du parseur HTTP tuent le poller (CORRIGÉS)

> Cette section couvre **trois** panics distincts, tous dans le même chemin de code et tous découverts par fuzzing pendant cet audit. Ils partagent le même impact : le thread du *poller* meurt.

### A.1 — `data[sep + 4..]` sur réponse courte

**Localisation** : `src/probe.rs:1169` (avant correctif) — `data[sep + 4..]` avec `sep = find_sub(...).unwrap_or(0)`.

**Scénario** : un serveur HTTP qui répond **1 à 3 octets** puis ferme la connexion (sans `\r\n\r\n`) fait paniquer le parseur sur `range start index 4 out of range for slice of length 2`. Ce panic survient **dans le thread du poller** (`lib.rs:410`, `poll_all` → `poll_one`), qui **meurt sans filet** : aucun `catch_unwind` dans tout le projet. Conséquence : **la supervision des serveurs s'arrête définitivement** — plus aucun scan, plus d'auto-restart, plus de détection d'état. L'UI reste servie (thread HTTP séparé) et affiche un état figé, sans aucun message d'erreur. En mode desktop (`windows_subsystem = "windows"`) le panic est **totalement silencieux** : pas de console.

**Preuve** (binaire pré-correctif compilé à part, instance isolée) :
```
AVANT-correctif : last_error=None   -> ❌ poller MORT (serveur SAIN jamais sondé)
APRES-correctif : last_error="réponse non JSON (0 octets)" -> ✅ poller VIVANT
```
Test déterministe sur la fonction : `AVANT → RESULT: PANIC` / `APRES → RESULT: mcp_up=false err=Some("réponse non JSON (0 octets)")`.

**Correctif appliqué** (`src/probe.rs`) :
```rust
let body_start = sep.saturating_add(4).min(data.len());
let mut body_bytes = data[body_start..].to_vec();
```
+ test de non-régression `probe_http_reponse_courte_sans_separateur_ne_panique_pas` (4 vecteurs).

### A.2 et A.3 — `dechunk()` : slice hors bornes + overflow usize

**Localisation** : `src/probe.rs:1190-1208` (avant correctif) — fonction `dechunk()`.

**Scénario A.2** : une réponse `Transfer-Encoding: chunked` dont le dernier chunk est tronqué (`5\r\nhello` sans CRLF final) fait paniquer sur `range start index 10 out of range for slice of length 8` — le `&data[i..]` avec `i` déjà au-delà de `data.len()`.

**Scénario A.3** : une taille de chunk hexadécimale absurde (`ffffffffffffffff\r\n`) provoque `attempt to add with overflow` sur `start + size`.

**Mesuré** : 2 panics sur 6 réponses chunked hostiles testées.

**Correctif appliqué** :
```rust
while i < data.len() {
    let Some(p) = find_sub(&data[i..], b"\r\n") else { break; };
    ...
    let end = start.saturating_add(size);
    if start > data.len() || end > data.len() { break; }
    out.extend_from_slice(&data[start..end]);
    let next = end.saturating_add(2);
    if next > data.len() { break; }
    i = next;
}
```
+ test de non-régression `dechunk_responses_hostiles_ne_paniquent_pas` (8 vecteurs hostiles + 1 chunked valide).

### Vérification finale du fuzz

**16 réponses HTTP/chunked hostiles** jouées contre le binaire corrigé : **0 panic**, toutes rejetées proprement avec un message d'erreur.

### Correctif complémentaire recommandé (non appliqué)

Un `catch_unwind` autour du corps du poller, ou au minimum un `panic::set_hook` qui journalise le panic sur disque (`mcc.log`) — aujourd'hui un panic est **totalement invisible** en mode desktop. C'est la cause racine commune des trois défauts : le code est correct, mais sa failure mode est fatale et silencieuse.

## 5. Défaut B — P0 : XSS stockée via les statistiques d'un pair (CORRIGÉ)

**Localisation** : `src/ui.rs:698` (`renderPeers`), `src/ui.rs:943` et `src/ui.rs:958` (`renderMachines`).

**Scénario** : `${st.up}` et `${st.total}` (statistiques d'un pair) étaient interpolées **sans `esc()`**. Ces valeurs proviennent du corps JSON renvoyé par un hôte **distant**. Or `probe_peer` (`src/probe.rs`) **n'exige aucune preuve** pour accepter un pair : il vérifie seulement que la réponse contient les clés `servers` et `stats`. Un attaquant du LAN peut donc se faire passer pour un command-center et injecter `<img src=x onerror=...>` dans les statistiques.

La CSP actuelle **n'arrête pas** ce vecteur : elle autorise explicitement `script-src 'unsafe-inline'` et les gestionnaires en ligne (`onclick=`) — ce n'est pas la barrière, l'échappement l'est.

**Impact théorique** : depuis le contexte JS de l'UI, le code injecté peut lire le code d'accès dans `localStorage` (`mcc.access`) et appeler `/api/action` → ajout d'un serveur stdio `cmd.exe /c …` = **exécution de commande**. Sur cette machine, l'auth est réelle → un pair malveillant ne peut pas exfiltrer le code sans qu'il soit déjà dans le navigateur ; mais le payload s'exécute dans la session de l'opérateur.

**Correctif appliqué** (`src/ui.rs`, 3 sites) : `esc()` sur `p.ui_port`, `st.up`, `st.total` et leurs équivalents `(peer.stats||{})`.

**Vérification** : la page servie par le binaire corrigé contient `${esc(st.up ?? '?')}` et `${esc((peer.stats||{}).up ?? '?')}` (0 occurrence des formes non échappées).

## 6. Défaut C — P2 : lecture stdio sans plafond de taille de ligne (CORRIGÉ)

**Localisation** : `src/probe.rs:1400` — `for line in reader.lines()`.

**Scénario** : un serveur MCP stdio (ou un processus lancé par `add stdio`) qui écrit une ligne unique de 300 Mo sans `\n` fait allouer 300 Mo d'un bloc par `BufRead::lines` — **mesuré : 314 572 800 octets lus en une `read_line`**. Le côté HTTP est plafonné (`MAX_PROBE_READ` 2 Mo, `MAX_PROBE_READ_SMALL` 256 Ko) ; le côté stdio ne l'était pas.

**Correctif appliqué** : `BufRead::lines()` remplacé par une lecture manuelle bornée (`read_until(b'\n', &mut buf)` + troncature à `MAX_PROBE_READ`). Vérifié : un serveur stdio écrivant 100 Mo sur une ligne donne désormais un **timeout propre**, sans allocationmassive ni panic.

## 8. Constats restants (non corrigés — documents)

### P2 — `manage.rs` a franchi 4 500 lignes (4 596)
Le littéral `Server { … 20 champs … }` est dupliqué ~15 fois. Toute évolution du modèle `Server` impose 15 retouches, et c'est la source de bugs silencieux (un champ oublié → `default` implicite). Correctif : un constructeur `Server::new()` + une fonction `Server::from_json` unique ; ~400 lignes d'économie.

### P2 — `poll_all` est séquentiel (`manage.rs:1254-1264`)
32 serveurs × sonde réseau = un cycle peut durer **> 15 s** (latence SSH mesurée jusqu'à 5 527 ms, moyenne 1 413 ms). Le `refresh_secs` de 15 s est donc déjà dépassé en pratique → les états affichés ont jusqu'à un cycle de retard. Correctif : pool borné (16-32 workers) au lieu d'une boucle séquentielle.

### P2 — `/api/state` n'expose pas `last_seen_ts`
`detail_json` ne renvoie pas `last_seen_ts` alors que `state_json` le stocke. Sans lui, impossible de distinguer « UP stable » de « UP figé » dans l'UI — c'est ce qui a rendu ce diagnostic de poller mort plus difficile. Correctif : ajouter `last_seen` au JSON de détail.

### P2 — `Referrer-Policy` / `Cache-Control` absents
Le code d'accès transite dans les en-têtes `X-MCC-Access`. `Cache-Control: no-store` sur `/api/*` éviterait qu'un proxy ou le cache du navigateur conserve une réponse contenant des données d'infrastructure. `Referrer-Policy: no-referrer` évite de fuiter l'URL de l'UI. `X-Frame-Options` est redondant (`frame-ancestors 'none'` est déjà présent).

### P3 — Le code d'accès n'est jamais effacé du navigateur
`localStorage.removeItem('mcc.access')` n'existe nulle part dans `src/ui.rs`. Sur un poste partagé, le code reste disponible pour l'utilisateur suivant du profil ; après rotation du code, l'ancien reste stocké et le dialogue se rouvre à chaque 401. Correctif : bouton « déconnecter » + effacement du stockage.

### P3 — `window.open` sans `noopener`
`ui.rs:500` ouvre la page des releases GitHub sans `noopener,noreferrer` : la page tierce peut accéder à `window.opener` (origine `http://127.0.0.1:<port>`) et donc lire le code d'accès dans `localStorage`. Correctif : `window.open(url, '_blank', 'noopener,noreferrer')`.

### P3 — Capability Tauri : 10 ports distants autorisés
`desktop/capabilities/main-remote-ui.json` autorise `http://127.0.0.1:5090` à `5099`. Le moteur fait un repli de port (5090→5099) : un processus tiers peut détourner un de ces ports et **hériter des permissions fenêtre** (drag/fermer) de l'app. Correctif : restreindre au port effectif, ou révoquer la capability si l'URL ne correspond pas.

### P3 — CSP `script-src 'unsafe-inline'` autorise les gestionnaires en ligne
La CSP est réelle mais `script-src 'unsafe-inline'` autorise `<script>` inline **et** les `onclick=`. Une future XSS s'exécute malgré tout. Ce n'est pas contournable par `+ 'self'` (un `<script>` inline n'est pas couvert par `'self'`) : la seule barrière est l'échappement — c'est pourquoi le défaut B ci-dessus est un vrai P0 et non un P3. Correctif à terme : migrer les handlers inline vers `addEventListener` + CSP `script-src 'self' 'unsafe-inline'` → `'nonce-…'`.

### P3 — Rendu DOM entièrement reconstruit à chaque cycle (5 s)
`render()` réécrit `innerHTML` de l'explorateur, du journal, des pairs et du détail à chaque tick. Effets : perte du focus et du scroll, et reset des `<details>` (repliés) — l'auditeur UI a relevé ce point. Correctif : rendu incrémental par `s.id`.

## 9. Points forts (à préserver)

- **Modèle de menace réellement tenu** : auth par code + Host/Origin/Content-Type + preuve HMAC à usage unique. Testé en direct contre l'instance bindée sur `0.0.0.0`, y compris le rejeu de preuve et le nonce inventé.
- **HMAC-SHA256 implémenté à la main, correct** : validé contre les vecteurs **NIST FIPS-180** (SHA-256) et **RFC 4231** (HMAC, cas 2 / clé courte / clé > bloc). La preuve de pair ne fait jamais transiter le secret.
- **Sanitize SSH exemplaire** : `ssh_safe` (liste blanche stricte, testée contre l'injection), `mcp_path_safe`, payload sans quote, session id `tr -cd 'A-Za-z0-9-_'` — la feature la plus risquée est la mieux défendue.
- **Zéro dépendance réseau** : `std` + `serde_json` seulement, HMAC et SHA-256 maison, `Cargo.lock` commité, surface supply-chain minimale.
- **Anti-DoS d'entrée** : corps 2 Mo, 64 connexions simultanées, headers 1 Mo, lectures réseau plafonnées (2 Mo / 256 Ko).
- **Écriture config atomique** (tmp+rename), **erreurs journalisées** (pas d'avalement silencieux), **garde anti double-spawn**, **auto-restart coupé après 3 échecs**.
- **CSP réelle** servie par le core (mesurée) + `nosniff` + `frame-ancestors 'none'`.
- **Tests qui testent le protocole** : faux serveurs HTTP/SSE/stdio, contrat pair, fingerprint LiteMCP à deux signaux, fingerprint FastMCP à 4 signaux, netstat/ss par colonne, roundtrip config, preuve HMAC (usage unique).
- **CI sérieuse** : `ci.yml` (fmt + tests + clippy strict tous targets) sur push/PR, `release.yml` (4 cibles core + 4 cibles desktop), **actions épinglées par SHA**, `permissions: contents: read` au workflow et `contents: write` limité au job release.
- **Hygiène git** : `.gitignore` complet (config, cache, e2e, repo niché, parasites Windows), 39 fichiers suivis tous légitimes, aucun secret dans l'historique.

## 11. Conclusion

L'audit du 2026-10-24 avait raison de pointer le trou de l'auth : il est **fermement refermé**, et cette fois **vérifié dynamiquement** et non par lecture de code. Le projet est en bon état : 75 tests verts, clippy strict propre, format propre, CI sur push/PR, SHA épinglés, zéro secret dans l'historique, HMAC correct contre RFC 4231.

Les vrais défauts trouvés cette fois sont **de nature différente** de ceux de l'audit précédent : ce ne sont plus des trous de conception mais des **défauts d'implémentation** — un slicing non borné dans le parseur HTTP, deux slicing/overflow dans `dechunk()`, trois interpolations oubliées dans le rendu des pairs, un `BufRead::lines()` sans plafond. C'est exactement le genre de défaut que les tests ne couvrent pas parce qu'ils n'imaginent pas la réponse hostile.

**La leçon qui en découle** : **le fuzzing des entrées réseau vaut plus qu'un test nominal**. Le fuzz de 16 réponses HTTP/chunked hostiles a trouvé en quelques minutes **trois panics** que 74 tests ne voyaient pas ; il est probable qu'une passe équivalente sur les en-têtes HTTP, le handshake stdio et les corps JSON de pair trouverait d'autres cas de bord. Corrigés, testé, et le plan d'action propose en priorité un `panic::set_hook` journalisé — pour que le prochain panic ne soit jamais silencieux.
